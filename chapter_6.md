# 6. Evaluation

Evaluating Large Language Models (LLMs) is a critical step in the AI development lifecycle.  Without evaluation, it is impossible to measure model improvement. Before collecting training data or initiating training pipelines, establishing a standardized evaluation benchmark (including test sets, metric definitions, and scoring scripts) is mandatory.

In real-world engineering, evaluation serves four primary functions:

- Model Selection: Different tasks require different models. Evaluation tells you which model is best suited for a specific scenario.

- Training Feedback: Did the model get better or worse after Supervised Fine-Tuning (SFT) or Reinforcement Learning from Human Feedback (RLHF)? Metrics provide an objective conclusion.

- Safety Compliance: Will the model output harmful content? Safety evaluations must be conducted before a model goes online.

- Alignment Verification: Does the model's behavior align with human expectations? Alignment evaluation ensures the model acts as intended.

The industry is shifting from Static benchmarks toward a comprehensive evaluation system centered on Dynamic, multi-dimensional, and human-preference-centric metrics. How we evaluate models has evolved through three distinct generations:

1. First Generation (2020-2022): Static Benchmarks. Dominated by classic datasets like MMLU and GSM8K. Severe Data Contamination, where models memorize the test set just to climb the leaderboards.

2. Second Generation (2023-2024): LLM-as-Judge + Human Evaluation. The rise of platforms like MT-Bench and Chatbot Arena. Focuses on multi-dimensional evaluation (Usefulness, Safety, Preference Alignment).

3. Third Generation (2025-2026): Dynamic Evaluation + Agent Evaluation. Platforms like LiveBench constantly change their questions to completely prevent leaderboard hacking. Platforms like SWE-bench/WebArena evaluate "what the model can do" rather than just what it knows. The core shift is from evaluating "Knowledge Memorization" to evaluating "Real-world Task Completion Ability".

In practice, evaluation follows a strict, escalating cost pipeline:

1. Automated Benchmark: Used for rapid screening.

2. LLM-as-Judge: Used for fine-grained assessment.

3. Human Evaluation: The final gatekeeper before release.

4. A/B Testing: Online validation with real users.

Automated evaluation is divided into three main categories based on the task:

1. Text Generation Metrics

- BLEU. Core Idea: Compares the n-gram overlap between generated text and reference text. It focuses heavily on Precision. Formula:

$$\text{BLEU} = \text{BP} \cdot \exp\left(\sum_{n=1}^N w_n \log p_n\right)$$

$p_n$: The n-gram precision (the ratio of n-grams in the generated text that appear in the reference text).

$N$: Maximum n-gram order (usually $N=4$).

$w_n$: Weight for each order (usually uniform, $w_n = 1/N$).

$\text{BP}$: Brevity Penalty. This prevents the model from artificially inflating its score by generating incredibly short, safe text.

BLEU only looks at literal overlap, ignoring semantics. For the long text generated by modern LLMs, BLEU is essentially useless.

- ROUGE. Core Idea: Also compares n-gram overlap, but focuses on Recall. It serves as a complement to BLEU. ROUGE-N measures n-gram overlap. The critical difference from BLEU is the denominator: ROUGE divides the matching n-grams by the total n-grams in the reference text, while BLEU divides by the total n-grams in the generated text. ROUGE-L is based on the Longest Common Subsequence (LCS).

$$R_{lcs} = \frac{\text{LCS}(X, Y)}{m} (Recall)$$

$$P_{lcs} = \frac{\text{LCS}(X, Y)}{n} (Precision)$$

$$F_{lcs} = \frac{(1 + \beta^2) \cdot R_{lcs} \cdot P_{lcs}}{R_{lcs} + \beta^2 \cdot P_{lcs}}$$

Like BLEU, it ignores semantics. Synonyms or paraphrasing will cause the score to drop drastically. Modern evaluation prefers BERTScore or LLM-as-Judge methods.

- BERTScore / BARTScore. These are semantic-level metrics based on pre-trained models. BERTScore calculates the maximum cosine similarity using hidden vectors, while BARTScore frames evaluation as a generation probability problem.

2. Classification & Comprehension Metrics. These are used for tasks like multiple-choice questions.

- Accuracy: Correct count / Total count.

- F1 Score: The harmonic mean of Precision and Recall. $F1 = \frac{2PR}{P+R}$

- AUC-ROC: Measures overall performance across different thresholds.

(Note: For multiple-choice questions, evaluation can be Generative, where answers are extracted using regex, or Probabilistic, where the probability of A, B, C, D is calculated and the highest is chosen).

3. Code Generation Metrics.

- Pass@k: You generate $k$ candidate solutions. If even one passes the unit tests, it is considered a success.  It calculates $1 - \text{probability of getting all answers wrong} = \text{probability of picking at least one correct answer}$. Formula:

 $$\text{Pass@k} = 1 - \frac{\binom{n-c}{k}}{\binom{n}{k}}$$

$n$: Total candidate solutions generated.

$c$: Number of correct candidate solutions.

$k$: The number of candidates sampled each time.

- Human eval.

There are two major philosophical and technical crises in model evaluation.

- Data Contamination (Data Contamination) is the biggest crisis of trust. It occurs when benchmark test data accidentally (or intentionally) leaks into the model's massive training corpus. The model isn't reasoning; it's just repeating what it memorized. Detection Methods include n-gram overlap detection, re-ranking methods, and using dynamic question banks like LiveBench.

- Goodhart's Law. This famous economic law perfectly applies to AI evaluation: When a measure becomes a target, it ceases to be a good measure. If developers train a model specifically to get a high score on MMLU, the MMLU score no longer reflects the model's actual general intelligence. The solution is to rely on comprehensive evaluation across multiple benchmarks.

## 6.1 Datasets

The landscape of Large Language Model (LLM) evaluation is vast and constantly evolving. Because different models are designed for different tasks, the industry categorizes evaluation benchmarks based on downstream applications. This document outlines the complete panorama of LLM evaluation datasets, categorized by their specific use cases: General Knowledge, Math, Code, Long Context, and Agent Abilities etc.

1. General Knowledge & Reasoning. These benchmarks test the model's fundamental understanding of the world, logical deduction, and ability to follow instructions.

- The MMLU Family. The classic MMLU benchmark covering 57 subjects (STEM, humanities, social sciences) from high school to expert levels. MMLU-Pro is a upgraded version. It expands the multiple-choice format to 10 options (up from 4), dropping the random guessing probability from 25% to 10%. It covers 14 subjects with significantly increased difficulty. It has gradually replaced the original MMLU. Use Case is evaluating broad general knowledge and cross-disciplinary reasoning.

- Expert-Level Reasoning. GPQA is written by PhD experts. Human experts outside their specific domain only score about 65%. It can differentiate the abilities of top-tier models to a certain extent. GPQA-Diamond is the most difficult subset of GPQA (physics, chemistry, biology). It is recognized as the most effective benchmark for differentiating top-tier models. Models like DeepSeek-R1, o1, and Claude 4 report their scores here.

- Factual Accuracy & Following Instructions. TruthfulQA is specifically tests whether a model will generate common false answers. Questions are designed to be things humans easily get wrong. It is crucial for evaluating factual accuracy, anti-misleading capabilities, safety, and alignment. SimpleQA is released by OpenAI. Tests the accuracy of short, factual Q&A. Unlike TruthfulQA, it focuses purely on knowledge accuracy rather than anti-misleading ability. DROP is a reading comprehension dataset requiring discrete reasoning. The model must perform operations like addition, sorting, and counting within paragraphs. (Main metric: 3-shot F1). IF-Eval (Instruction Following Evaluation) evaluates the model's ability to follow instructions, including format constraints and content constraints. (Main metric: Prompt Strict mode).
  
2. Mathematical Reasoning. These benchmarks evaluate step-by-step logic, calculation, and advanced mathematical theorem proving. GSM8K (Foundation) has 8.5K elementary school math word problems requiring 2-8 steps of reasoning. Because mainstream 2024 models are already nearing saturation (>90%), it is now considered the entry-level evaluation standard for basic mathematical reasoning. MATH-500 has 500 highly difficult competition problems selected from the MATH dataset, covering 7 subcategories like algebra and geometry. In 2025, DeepSeek-R1 reached 97.3% and o1 reached 96.4%. Though approaching saturation, it remains a standard metric for all mainstream model releases. AIME 2024 has real questions from the American Invitational Mathematics Examination. Extremely difficult. In 2025, this is the math evaluation with the highest differentiation. For example, DeepSeek-R1 reached 79.8%, o1 reached 79.2%, while GPT-4o only hit 9.3%.

3. Code Generation. The evolution of code benchmarks moves from basic function generation to real-world, repository-level bug fixing.

- HumanEval (Foundation): 164 Python programming problems. The classic standard. Note: Post-2024, it is nearing saturation (mainstream models >80%) and is being replaced by LiveCodeBench, but remains useful for baseline comparisons.

- LiveCodeBench: Dynamically and regularly scrapes new problems from platforms like Codeforces and LeetCode. This strictly prevents data contamination. It supports Pass@1 and Chain-of-Thought (COT) evaluation modes and is the most mainstream code evaluation for 2025-2026.

- SWE-bench Series: The ultimate test for evaluating a model's ability to automatically fix real bugs. Based on real GitHub Issues and Pull Requests. SWE-bench: 2294 Issue-PR pairs. Results can be unstable due to vague issue descriptions. SWE-bench Verified: Human annotators verify one by one that the issue can actually be solved via code modification. Keeps about 500 highly reliable problems. SWE-bench Lite: A streamlined subset of 300 high-quality problems for faster iteration. SWE-bench Multimodal: Expands to include visual information like screenshots and UI diagrams.

- Codeforces Rating: Evaluates models directly on the real programming competition platform Codeforces, outputting an Elo Rating. It is the most intuitive indicator of competitive programming ability.

- Aider Polyglot: Evaluates the model's code modification ability across multiple programming languages.

4. Long Context Evaluation. Evaluates the model's ability to retain, retrieve, and reason over massive amounts of text. LongBench v2 is an upgraded version adding more long-context reasoning tasks with higher difficulty. DeepSeek-V3 achieved 48.7% here. It is the standard long-text evaluation for 2025. RULER features configurable context lengths (4K-128K) and includes tasks like multi-needle/multi-hop retrieval, variable tracking, and aggregation statistics. Useful for pinpointing a model's effective context window length. Needle In A Haystack (NIAH) is the classic test where a key piece of information is inserted into a massive text block to see if the model can accurately locate and extract it.

5. Agent Evaluation. Evaluates the model's ability to act autonomously, plan, interact with environments, and use tools. The slide breaks this down into four pillars: Tool Use, Multi-step Planning, Error Recovery, and Environment Interaction.

- WebArena: Evaluates Agents in a real web environment. The model must complete end-to-end tasks like searching, shopping, or posting on forums on a real website.

- OSWorld: Evaluates Agents in a real operating system environment (Ubuntu/Windows/macOS), requiring tasks like file management and application usage.

- AgentBench: A comprehensive evaluation covering 8 different environments, including operating systems, databases, knowledge graphs, and digital card games.

- ToolBench: A massive tool-use evaluation containing 16,000+ real APIs.

- SWE-bench Verified (Revisited): Beyond coding, it evaluates Agent capabilities in terms of repository navigation, problem location, and multi-file editing.

6. Embedding Evaluation. Evaluates models specifically designed to convert text into vector representations, crucial for RAG (Retrieval-Augmented Generation) systems. MTEB (Massive Text Embedding Benchmark) / MTEB v2: The absolute standard reference for selecting an Embedding model. It is massive, covering 8 task types including classification, clustering, retrieval, re-ranking, and semantic similarity.

7. Evaluation Platforms. The underlying software frameworks used by engineers and researchers to actually run these massive datasets.

- lm-evaluation-harness: Developed by EleutherAI, this is the industry standard. It supports over 200 benchmarks and backends like HuggingFace and OpenAI APIs. Almost all open-source models (like Qwen and LLaMA) publish results based on this specific framework. Ideal for rapid, multi-dimensional standardized testing.

- LM Arena (formerly Chatbot Arena): Developed by LMSYS. This is completely different from static datasets; it is an open evaluation platform utilizing an Elo scoring system. Users submit prompts, and models generate anonymous answers. Human users then blindly vote on which answer is better. By 2025-2026, it expanded to include coding, long-text, multi-modal, and Agent leaderboards. It is widely considered the most credible open evaluation because it best measures the actual user experience.



## 6.2 Training Evaluation

### 6.2.1 Probabilistic Probe

When training and evaluating Large Language Models (LLMs), standard automated benchmarks might not always capture the nuanced, specific capabilities or facts we want the model to learn. To address this, engineers utilize a highly targeted technique known as the Probabilistic Probe. The fundamental motivation behind a Probabilistic Probe is precision. Sometimes we want to "precisely observe whether a model has learned a certain fact or how much probability it assigns to a specific sentence". It is a highly specialized tool designed to observe a very specific capability of the model. The underlying logic is incredibly simple: observe whether the probability of a specific token or sentence increases over time. However, this precision comes with a major engineering trade-off: these probe test sets cannot be easily generated in bulk. They typically require trainers to construct them manually, item by item, to ensure they exactly measure the intended metric. Conducting a Probabilistic Probe involves a strict, manual two-step process:

1. Manual Design and Selection. First, engineers must "manually design or select sentences with specific knowledge or stances in advance". Because the probe is testing targeted knowledge or values, the dataset must be carefully curated.

2. Probability Checking. Next, for every sentence in the curated test set, engineers look at the "predicted probability" that the model assigns to the whole sentence or to a specific key token within it.

There are three vital rules for effectively using Probabilistic Probes in a real-world training pipeline:

1. Manual Construction is Mandatory: This type of probe usually requires manually and meticulously constructing the test set. This is the only way to truly capture the specific knowledge points or values you care about.

2. Focus on Training Iterations: The primary goal is to observe the model during its training iterations to see if the probability of "correct facts" is getting higher, and if the probability of "wrong facts" is getting lower.

3. The Golden Rule of Probing: Similar to benchmark modification, probabilistic probes can be arbitrarily constructed according to one's own preferences. What we focus on observing is the trend of the indicator's change, not the absolute size of the indicator.

Do not worry if the absolute probability score is low (e.g., $0.05$); what matters is whether that score grows to $0.10$, $0.20$, etc., as training progresses, indicating that the model is actively learning the targeted concept.


## 6.3 SFT Evaluation

Evaluating a model after Supervised Fine-Tuning (SFT) is a vastly different process than evaluating a foundational pre-trained model. While pre-training evaluation focuses purely on broad knowledge capacity, SFT evaluation focuses on usability, alignment, and specific task execution. The foundation of SFT evaluation is a high-quality evaluation dataset. The tasks in this test set must explicitly match the task types present in the SFT training data. A model's performance on this specific test set determines whether it is ready for production. Unlike pre-training, SFT evaluation traditionally aligns with the classic 3H Principles:

- Helpfulness: Does the model actually assist the user?

- Honesty: Is the model factually accurate?

- Harmlessness: Is the model safe to use?

However, in real-world engineering, companies rarely stick to just these three abstract principles. Instead, they define specific, practical metrics based on their product needs, such as:

- Instruction Following 

- System Prompt Penetration 

- Content Accuracy

- Hallucination Generation

- Safety

During evaluation, each of these specific dimensions receives an independent score. These scores are then combined using a customized weighting formula to determine the overall usability of the response.  If a model fails a test case, engineers can immediately see which specific dimension dropped, allowing for targeted case analysis against the training data.

When evaluating, you must understand the entire LLM system. If your company has a strict front-end safety filter, it is meaningless to heavily penalize the raw model for safety issues. If you have a powerful RAG (Retrieval-Augmented Generation) system, overly focusing on the raw model's hallucinations might be misguided. You must evaluate the specific capabilities that the LLM cannot rely on external systems to catch or fix.

Currently, the industry relies on two main methods to conduct these evaluations: Machine Evaluation and Human Evaluation. Machine Evaluation involves using a powerful model (like GPT-4) as the Judge. The most critical aspect here is prompt design, because LLMs have severe inherent biases. When comparing Answer A and Answer B, the Judge model naturally leans toward picking A. The Judge model naturally prefers longer answers.  If you ask a model to score the exact same perfect answer three times, it might output 3, 4, and 5 randomly. The mitigation is to use highly standardized prompts. Furthermore, providing the Judge model with a Standard Reference Answer significantly stabilizes the scoring, as the Judge can calculate similarity between the candidate and the "gold answer." Contrary to popular belief, manual human evaluation remains the mainstream strategy for LLM companies. It is not as expensive or cumbersome as assumed (often cheaper than massive API calls to OpenAI's o1). Humans have long-term memory. The most time-consuming part of SFT evaluation isn't reading the answer, it's understanding the prompt. If evaluators are very familiar with the prompt, they immediately know what mistakes the model's answer is likely to make and what the focus should be, making efficiency extremely high. As long as the test set doesn't change daily, human evaluators quickly memorize the prompts. After one or two rounds, their evaluation speed easily matches or exceeds Machine Evaluation.

SFT evaluation must be comparative evaluation; looking directly at the model's performance on the test set provides no guidance. You must always compare the current version (SFT v2) against the previous baseline (SFT v1). If SFT v2 shows a significant drop in a specific capability (e.g., Capability 'A') compared to SFT v1, engineers must trace back to the training data. There are four potential root causes:

- Data Degradation: The training data for Capability A was updated, but the new quality is worse than the previous version. Engineers must manually review the new data.

- Data Imbalance: The overall volume of training data increased, causing the relative proportion of Capability A data to shrink, leading to slight underfitting.

- Hyperparameter Issues: Specific training parameters for this run were set incorrectly.

- Statistical Fluctuation: The drop might just be random variance. The solution is to isolate a specific bad case from SFT v2. Force both SFT v2 and SFT v1 to predict that same prompt multiple times and analyze the sampling variance.

 
### 6.3.1 LLM-as-Judge

The traditional methods of evaluating language models (like static datasets or human annotation) face significant bottlenecks in cost, speed, and scalability. To solve this, the industry has embraced the "LLM-as-Judge" paradigm, an evaluation method that uses powerful language models to assess the outputs of other models. Below is the basic workflow:

1. A user prompt is given to the Model Under Test.

2. The model generates an answer.

3. Both the prompt and the answer are fed into a Judge Model (e.g., GPT-4 or Claude).

4. The Judge Model outputs a score or a win/loss decision, achieving 80%+ consistency with human judgment.

Compared to manual human annotation, LLM-as-Judge offers massive advantages in three areas:

- Cost: $0.01 per question vs. Human $1-5 per question.

- Speed: Minutes vs. Days.

- Consistency: $75-90\%$ vs. Human-to-Human consistency of $70-85\%$.

When designing an LLM-as-Judge prompt, there are three primary architectural modes used to evaluate answers.

- Pairwise Comparison. This is the most commonly used mode. The Judge model is given the same user prompt and two different answers (Answer A and Answer B) from two different models. It is then asked to judge which one is better, outputting A, B, or Tie. In this way relative evaluation is more stable. However, it can only provide a relative comparison, not an absolute score. Furthermore, because every model must be compared against every other model, the evaluation cost scales quadratically: $O(n^2)$.

- Pointwise Scoring. In this mode, the Judge model is given a prompt and a single answer, and must directly output an absolute score (usually on a scale of 1-10) along with a JSON reason. The evaluation cost is $O(n)$, and each answer can be evaluated entirely independently. However, scores between completely different questions are hard to compare, and the Judge's scoring scale might drift over time.

- Reference-based Evaluation. This mode provides the Judge with a Standard Reference Answer. The Judge's job is simply to compare the model's output against the standard answer to determine the degree of match. This is the most "evidence-based" mode. It is perfect for QA tasks or summarization tasks where a definite factual answer exists. However, the hardest part of writing the prompt for this mode is instructing the Judge to distinguish between "missing information" and "extra but correct information," ensuring it doesn't mistakenly penalize good supplementary content as a hallucination.

Because Judges are still LLMs, they carry inherent statistical biases that must be mitigated through engineering. 

- Position Bias. In Pairwise comparison, the Judge tends to choose the answer placed first. If you swap the positions of Answer A and Answer B, the Judge's final decision might completely reverse. To solve this, you must run every test twice, randomly swapping the A/B order. You only accept the result if the model chooses the same actual answer both times; if the results are inconsistent, it is judged as a tie.

- Verbosity Bias. The Judge tends to give higher scores to longer answers. Even if the core information is identical, and the longer answer is filled with fluff, the Judge will mathematically prefer the longer text. This heavily impacts Pointwise scoring. You must explicitly instruct the model in the prompt to ignore length ("please ignore length differences, only evaluate content quality"). Alternatively, you can use automated correction metrics like AlpacaEval 2.0's Length-Controlled Win Rate.

- Self-Enhancement Bias. A Judge tends to give high scores to its own outputs. If GPT-4 judges a GPT-4 answer, the score will be systematically biased upward. This is most severe in self-evaluation scenarios. Use a different model as the Judge (e.g., using Claude to judge GPT-4), or adopt a multi-model voting mechanism where multiple different Judges average their scores.

As of 2026, the mainstream approach to building an LLM-as-Judge framework relies on Multi-dimensional Independent Scoring. You do not just ask "is this good?"; you ask the Judge to score specific core dimensions:

- Helpfulness: Did it actually solve the user's problem?

- Correctness: Factual accuracy.

- Coherence: Logical consistency.

- Safety: A one-vote veto system for harmful content.

- Instruction Following: Did it obey specific formatting rules?

When building an LLM-as-Judge pipeline, engineers should study these three industry standards:

- MT-Bench: Uses 80 multi-turn questions across 8 categories with a 10-point scale.

- Arena Hard: Contains 500 highly discriminative, difficult prompts.

- Chatbot Arena: The gold standard for Elo rating rankings based on human/judge preference.
The SFT process is a continuous loop. Cases where the score improves become our good experience for cleaning data; cases where the score worsens become the target for the next version's optimization. Repeated iteration is all that is required.

## 6.4 Needle In A Haystack

The Needle In A Haystack test is a critical evaluation benchmark designed specifically for modern Large Language Models (LLMs) that handle massive amounts of text. The Needle In A Haystack test focuses on examining the model's information extraction and understanding capabilities within ultra-long contexts. It works by taking a massive block of text and randomly inserting specific "key information" into it to form a prompt for the LLM. The test observes whether the model can successfully dig through the noise to extract those specific key details. Ultimately, this reflects the LLM's foundational capacity to comprehend and process long-form text. Conducting this test involves a strict two-step process:

1. Constructing the Haystack: First, prepare a relatively long text, typically consisting of thousands of words or more. This text acts as the "haystack" because it is filled with various redundant or completely irrelevant information. Inside this massive block, key details (the "needles") are randomly inserted.

2. Retrieval: Next, ask the model to answer one or more questions. The catch is that these questions can only be answered by relying on the key parts hidden deep within the text.

As models have advanced, the basic test has evolved into four distinct, progressively difficult variants:

- Single Information Retrieval Task. Only one key piece of information is hidden in the long article; see if the model can accurately find it. This evaluates the LLM's ability to extract a single, isolated fact. It tests the model's precise recall of specific details buried within a broad narrative. This specific setup corresponds exactly to the original Needle In A Haystack test.

- Multiple Information Retrieval Task. Multiple scattered key pieces of information are buried in the article, requiring synthesis to answer. This variant explores the LLM's ability to retrieve multiple related pieces of information from a long text simultaneously. It is designed to simulate complex, real-world scenarios where a user queries a comprehensive document and requires answers drawn from various sections.

- Multiple Information Reasoning Task. After retrieving multiple key pieces of information, further reasoning and integration are required to get the result. This pushes the model beyond simple extraction. It evaluates long-context ability by requiring the model to extract multiple key information fragments and then comprehensively understand and logically combine those fragments to deduce the correct answer.

- Ancestor Tracing Challenge / ATC. Similar to complex genealogy/bloodline/kinship reasoning, requiring multi-layered logical connections. By designing a "kinship needle," this tests the LLM's capacity to handle multi-layered logical challenges in realistic long texts. Through a series of logical reasoning questions, it tests the model's memory and its ability to analyze every single detail. Notably, in this ATC task, the standard "irrelevant text" (the Haystack) is completely removed. Instead, all the text provided is designed as key information. The LLM must comprehensively apply all the content within the long text and actively reason through it to answer accurately.
